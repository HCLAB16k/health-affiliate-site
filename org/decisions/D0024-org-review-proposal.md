## 3. 共通項（何が繰り返し起きているか）

1. **「要約すると条件が落ちる」**: 要点・X・meta を短くするたびに、主体・対象・条件・片側の数字が落ちる（事実性の指摘の大半）。書き手と審査の間に「原文との突き合わせ」を専門にする工程が無い。
2. **機械で見つけられる誤りを人（エージェント）が見つけている**: 更新日・build 漏れ・アンカー・#PR・要点内の番号・文の長さ。毎回審査の手間と往復を使っている。
3. **「頼まれた範囲」と「オーナーが期待する範囲」のずれ**: 要点だけ直して本文が残った、反映待ちを「公開済み」と報告した、など。公開後に「読者から見て完了か」を確かめる工程が無い。
4. **作る人はいるが、育てる人がいない**: 公開後の記事（古い統計・持ち越し・リンク切れ）と、X の反応の測定を担当する部署が無い。
5. **収益の持ち主がいない**: 商品企画部は案件単位で呼ばれるだけで、ASP の申請・承認状況・リンクの空き枠を継続して追う役が無い。

## 4. 提案

### A. すぐやる（コスト小・効果大）
| # | 内容 | 期待効果 |
|---|---|---|
| A1 | **自動品質チェック（CI）**: PR ごとに `scripts/lint_site.py` を GitHub Actions で実行。更新日と dateModified/sitemap の一致、要点内の番号・上付き、→アンカーの存在、#PR とアフィリエイトリンクの整合、disclaimer/pr-badge、文の長さの閾値、X キューの --check | 技術系の指摘（74件分）を審査前に機械で止める |
| A2 | **道具の付与**: 編集部に Bash（readability・lint の実行に限定）、レビュー部に Edit | 実測の代行・回避操作をなくす |
| A3 | **完了確認の工程**: org-cycle の最後に「公開後確認」（本番 URL で反映・表示・依頼範囲の全数確認、スマホ幅のスクリーンショット）を必須化 | 範囲のずれ・反映待ちの誤報告をなくす |

### B. 新しい部署（Routine か案件の中で呼ぶ）
| # | 部署 | 担当 | 頻度・コスト目安 |
|---|---|---|---|
| B1 | **事実確認部（fact-checker）** | 編集部の原稿を審査の前に原文と突き合わせ、「主体・対象・条件・数字・訳・範囲」の対照表を作る。直すのは編集部、判定はレビュー部（役割は分ける） | 毎案件。審査の往復が1回減れば相殺できる見込み |
| B2 | **収益・提携部（partnerships）** | ASP（A8・もしも・afb）の申請リスト、承認状況、記事ごとのリンクの空き枠、リンク切れ・終売の監視、オーナーへの依頼のとりまとめ（週1回にまとめて出す） | 週1回（Routine） |
| B3 | **保守部（maintenance）** | 確認日が古い数値・価格の再確認、外部リンク切れ、backlog の持ち越し（#58 等）の消化、統計の更新 | 週1回、1〜2記事 |
| B4 | **読者体験部（UX）** | 本番ページをスマホ幅で月1回巡回し、読みにくさ・見づらさ・導線の問題を起票（今回オーナーが見つけた種類の問題を先に見つける） | 月1回 |

### C. 既存部署の整理
- **分析部を定期実行に戻す**: 月曜の KPI 更新を分析部に任せ、Search Console のクエリから「表示ありクリック0」の記事を毎週1本起票（タイトル改善の枠）。
- **マーケティング部を正式なエージェントにし、X の効果測定を持たせる**: 型ごとの反応（オーナーのスクショ、将来は API）を記録して型ガイドを更新。channel-strategist は戦略・設計に専念。
- **商品企画部**は B2 に吸収するか、B2 の下で案件ごとに呼ぶ。

## 5. 運用の変更
- 週のリズム: 月 KPI＋分析（分析部）／火 新記事＋保守1本／木 トレンド＋収益・提携の週報／月1 UX 巡回。
